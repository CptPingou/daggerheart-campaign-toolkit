# P2.6.2d — Schéma canonique `adversary.hunting` + exports Foundry / BeastVault

**Statut : DRAFT DE SCHÉMA — à valider avant code**

## 1. Objectif

Définir une extension canonique unique pour les adversaires de chasse afin que la même source alimente :

```text
DH Data
├── export Foundryborne
└── export Obsidian / BeastVault
```

Sans créer une seconde fiche Monster Hunter parallèle.

Le principe est :

```text
adversary canonique
├── données Daggerheart normales
└── hunting
```

`hunting` contient uniquement les informations qui ne relèvent pas déjà du modèle adversaire Daggerheart.

---

## 2. Frontière de responsabilité

Les données Daggerheart restent dans leurs champs canoniques existants :

```text
tier
role
difficulty
thresholds
hp
stress
attack
experiences
features
actions
description
...
```

L'extension Hunting ne doit pas dupliquer ces données.

Elle porte seulement les primitives propres à la chasse :

```text
footprint
tags
mobility / state contextuel
reactions
```

## 4. Footprint

Le footprint décrit l'occupation spatiale du monstre sur le plateau :

```json
{
  "footprint": {
    "width": 2,
    "height": 2
  }
}
```

Exemples :

```text
Tetsucabra   → 2 × 2
Reine Vespoid → 2 × 2
```

Le moteur ne doit pas déduire automatiquement des règles de portée, de collision ou de mouvement à partir de cette taille.

Le footprint sert d'abord à l'affichage / placement / intégration plateau.

---

## 5. Tags Hunting

Les tags décrivent des propriétés de chasse utilisées par d'autres systèmes :

```text
Flying
Burrower
Carnivore
Herbivore
```

Ils servent notamment aux interactions déjà prévues :

```text
Flying    → Filet
Burrower  → Mine
Carnivore → Viande
Herbivore → Fruit
```

Ils doivent rester des identifiants stables et peu nombreux.

Exemples :

```json
["herbivore", "burrower"]
```

pour Tetsucabra.

```json
["flying"]
```

pour la Reine Vespoid.

---

## 6. Mobilité / état contextuel

La propriété de vol de la Reine Vespoid ne doit pas nécessairement devenir un état Daggerheart générique.

Le schéma candidat peut expliciter :

```json
{
  "mobility": {
    "mode": "flying",
    "state": "elevated"
  }
}
```

Cette information est exploitable par :

- l'interface de chasse ;
- les règles contextuelles de portée ;
- les cartes / pièges ;
- l'export Foundry ;
- la documentation BeastVault.

La sémantique exacte de `elevated` devra être définie séparément si elle devient une règle mécanique générique.

---

## 7. Hunting Reactions

Chaque adversaire de chasse peut définir :

```text
normal
fear
```

### Reaction normale

Déclencheurs :

```text
Réussite + Fear
Échec + Hope
```

### Fear Reaction

Déclencheur :

```text
Échec + Fear
```

La Fear Reaction peut :

- s'appuyer sur la réaction normale ;
- ajouter une conséquence ;
- modifier le terrain ;
- créer un déplacement ;
- appliquer un effet ;
- utiliser une autre primitive propre au monstre.

Elle ne doit pas automatiquement devenir « attaque + dégâts supplémentaires ».

## 10. Export Foundryborne

La cible reste un **Actor adversary natif**.

L'extension Hunting est exportée dans les flags Toolkit :

```text
Actor
├── system              # Daggerheart natif
├── items / features    # Daggerheart natif
└── flags
    └── daggerheart-campaign-toolkit
        └── hunting
```

Exemple :

```js
actor.flags["daggerheart-campaign-toolkit"].hunting
```

Contenu :

```json
{
  "schemaVersion": 1,
  "footprint": {
    "width": 2,
    "height": 2
  },
  "tags": [
    "flying"
  ],
  "mobility": {
    "mode": "flying",
    "state": "elevated"
  },
  "reactions": {
    "...": "..."
  }
}
```

### Principe

Foundryborne reste responsable :

- des stats ;
- des attaques ;
- des HP / Stress ;
- des actions adversaires ;
- des features Daggerheart.

Le Toolkit reste responsable :

- des tags Hunting ;
- du footprint ;
- des Hunting Reactions ;
- de l'UI / runtime Hunting.

---

## 11. Export Obsidian / BeastVault

La même source canonique est rendue en note BeastVault.

Exemple :

```markdown
## Hunting

**Footprint:** 2×2
**Tags:** Flying
**Mobility:** Flying / Elevated

### Reaction — Crache-venin

Trigger: Success + Fear or Failure + Hope.

The Queen Vespoid reacts against the Opener.
Defensive Support window available.

### Fear Reaction — Nuée paralysante

Trigger: Failure + Fear.

Resolve Crache-venin, then apply the additional paralysis consequence.
```

Le bloc Hunting est documentaire et n'altère pas la structure BeastVault normale de l'adversaire.

## 13. Ce que P2.6.2d ne décide pas encore

Cette passe ne fige pas encore :

- l'automatisation des réactions ;
- le widget / onglet Foundry Hunting ;
- la sémantique mécanique complète de `elevated` ;
- les règles de poison / paralysie ;
- les interactions Filet / Mine / appâts ;
- le format final de toutes les `resolution.kind`.

Ces décisions doivent être prises à partir d'un vertical slice réel, pas anticipées dans le schéma.

---

## 14. Critères de validation

P2.6.2d est GREEN si le modèle suivant est accepté :

- adversaire canonique unique ;
- pas de fiche Monster Hunter parallèle ;
- données DH natives non dupliquées ;
- extension `hunting` dédiée ;
- footprint stocké dans Hunting ;
- tags Hunting stables ;
- mobilité contextuelle possible ;
- `normal` + `fear` pour les Hunting Reactions ;
- export Foundry dans les flags Toolkit ;
- export BeastVault en section Hunting ;
- Tetsucabra et Reine Vespoid représentables sans cas spécial structurel.
