# P2.6.1 — Contextual Domain primitive

**Statut : CRISTALLISÉ**

## Intention

Un **Contextual Domain** est un cadre de capacités lié à un contexte narratif de campagne, distinct des Domaines de classe Daggerheart.

Il permet au MJ d'attribuer des cartes représentant ce qu'un personnage a acquis, appris, obtenu ou rendu possible dans un contexte particulier.

Exemples :

- **Hunting** — techniques de chasse et rôles dans l'Engagement ;
- **Dragonmark / House** — relations, privilèges, contacts et capacités institutionnelles ;
- **Mythos** — connaissances, fragments et capacités liées aux découvertes.

Un personnage peut appartenir simultanément à plusieurs Contextual Domains.

## Doctrine

Les Contextual Cards ne constituent pas une seconde progression de type deckbuilder.

- Leur acquisition est **narrative et pilotée par le MJ**.
- Le moteur générique n'impose ni niveau, ni XP, ni Vault, ni loadout.
- Un domaine particulier peut imposer ses propres contraintes d'usage.
- Une carte reste une vraie capacité de jeu et peut utiliser les ressources Daggerheart normales : Hope, Stress, Armor, etc.
- Un domaine peut également posséder un état ou une ressource temporaire qui lui est propre.

## Modèle générique

```text
Character
├── Daggerheart progression
│
├── Contextual Domains
│   ├── Hunting
│   ├── Dragonmark / House
│   └── Mythos
│
└── Equipment
    └── independent progression
```

Le moteur distingue :

```text
ContextualDomain
├── id
├── label
├── presentation
├── cardTypes
├── constraints
├── rules
└── state

ContextualCard
├── id
├── domainId
├── type
├── name
├── rules
├── costs
├── prerequisites?     # facultatif
└── presentation
```

## Types de cartes

Une carte possède **un type unique** dans son domaine.

Le moteur ne donne aucune signification universelle à ce type.

Exemples :

```text
Hunting
├── Opener
├── Finisher
└── Support
```

Un futur domaine de Maison pourrait utiliser des types entièrement différents.

Une carte multi-type n'est pas retenue : si deux fonctions mécaniques sont différentes, elles doivent être représentées explicitement plutôt que fusionnées artificiellement.

## Attribution

L'acquisition d'une Contextual Card est narrative.

Le MJ peut attribuer ou retirer une carte lorsque la fiction, une récompense, une relation, une découverte ou un événement le justifie.

Le moteur générique ne calcule pas automatiquement cette acquisition.

Des `prerequisites` dynamiques pourront être supportés si un domaine en a besoin, mais ils restent **facultatifs**. Aucun moteur complexe de conditions n'est requis pour le premier vertical slice.

## Contraintes propres au domaine

Le moteur générique ne possède pas de règle de préparation.

Chaque Contextual Domain peut définir ses propres contraintes.

Exemple Hunting :

```text
maxCardsPerCharacter: 2
```

La contrainte exacte sur les types Opener / Finisher / Support sera définie avec Engagement en P2.6.2.

Elle ne doit pas être généralisée aux autres Contextual Domains.

## Ressources

Une Contextual Card peut utiliser directement l'économie Daggerheart :

```text
Hope
Stress
Armor
HP
```

Un domaine peut également définir un état temporaire propre :

```text
Hunting
└── Opportunities
```

Le moteur générique sait conserver/manipuler cet état, mais n'interprète pas sa signification.

Les règles du domaine restent la source d'autorité.

## Équipement

Les Contextual Cards sont découplées de l'équipement.

Une technique de chasse n'est pas intrinsèquement une technique de Greatsword, d'Arc ou de Lance.

Ainsi :

```text
True Charge
type: Finisher
```

peut être utilisée avec des armes différentes.

Le contour fictionnel change :

```text
Greatsword → frappe pleinement chargée
Bow        → tir concentré
Lance      → estoc préparé
```

mais la mécanique de la carte reste la même.

L'arme possède sa propre progression :

```text
Weapon
├── native profile
├── native Weapon Features
└── Augments
```

La technique appartient au personnage.

## Présentation Foundry

Les Contextual Cards doivent être de **véritables cartes visuelles** dans Foundry.

Elles doivent être immédiatement distinguables :

```text
Daggerheart Domain Card
Hunting Card
House / Dragonmark Card
Mythos Card
```

La réutilisation de primitives techniques ou visuelles Foundryborne est souhaitable lorsqu'elle est propre, mais une Contextual Card ne devient pas pour autant une Domain Card canonique.

## Source d'autorité

```text
Classe / domaine canonique
    → progression Daggerheart

Capacité acquise par la fiction dans un contexte
    → Contextual Card

Modification persistante d'une arme
    → Augment / Weapon Feature

Règle commune à un contexte
    → Contextual Domain
```

## Premier consommateur : Hunting

Hunting servira de vertical slice de la primitive.

Il devra démontrer :

- attribution MJ de cartes ;
- maximum de 2 cartes par personnage ;
- types uniques Opener / Finisher / Support ;
- consommation de Hope / Stress ;
- état temporaire Opportunités ;
- interaction entre plusieurs chasseurs ;
- aucune dépendance obligatoire à une famille d'arme.

## Décision reportée à P2.6.2

La règle empêchant un chasseur de devenir une boucle autonome :

```text
Opener → Finisher
```

n'est volontairement pas codée comme une contrainte générique de composition.

P2.6.2 doit d'abord chercher à rendre la coopération obligatoire **par la règle d'Engagement elle-même**.

Une interdiction de combinaison de cartes ne sera ajoutée que si le protocole d'Engagement ne suffit pas.

## Validation

P2.6.1 est considéré cristallisé avec les décisions suivantes :

- plusieurs Contextual Domains simultanés : oui ;
- acquisition : narrative, contrôlée par le MJ ;
- loadout générique : non ;
- type de carte : unique ;
- prerequisites dynamiques : possibles mais facultatifs ;
- ressources Daggerheart : utilisables ;
- ressources/états propres au domaine : possibles ;
- cartes Foundry visuelles : oui ;
- contraintes de cartes : définies par chaque domaine ;
- équipement et techniques contextuelles : découplés.
